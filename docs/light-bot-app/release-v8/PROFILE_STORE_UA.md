# Canonical production profile/Bot store — локальна реалізація

Створено окремий production store, який зберігає App profile, Bot session, durable inbox receipt та pending message outbox однією транзакцією. Він повторно використовує чисті `createBotState`, `handleBotInput`, `parseProfileRequest` і `applyProfileMutation`; isolated store, його pool, synthetic fixtures та `simulationOnly:true` snapshot/action types не імпортуються і не перетворюються на production casts.

Автор працював лише з локальними source/tests та цим документом. Реальні DB, Replit, Telegram, production settings, legacy rows і секрети не використовувалися. Незалежне приймання, actual PostgreSQL, writer cutover і delivery цим документом не заявляються.

## API і довірені входи

`createProductionProfileStore({pool, enabled?, expectedControlEpoch, context, now?, verifiedSubscriberMappings?, verifyEmptyAccount?})` не підключається до DB при імпорті/створенні. `enabled` за замовчуванням false; `expectedControlEpoch` — positive safe integer з trusted server configuration. `pool` структурно сумісний із `pg.Pool`; немає імпортованого global pool або default fetch.

- `snapshot(verifiedPrincipal)` повертає `ProductionProfileSnapshot`: `runtime:'production'`, profile, sessionId, revision, actual serverNow, scoped catalog/plans. Перший виклик у дозволеному canonical mode може виконати одноразовий bootstrap. Read-only shadow route не повинен підключати цей метод до activation.
- `commitProfileMutation(principal, unknownRequest)` застосовує чинний closed `ProfileRequest` із mandatory expectedSessionId/revision. Підтримує add, replace, rename, delete, primary, move, location pause/notifications/policy та preferences. Власник, цілий profile і довільний binding не приймаються з request.
- `commitBotInput(principal, {input, expectedSessionId?, expectedRevision?})` виконує той самий Bot engine над тією самою state row. Trusted Telegram ingress **не передає** CAS: provider update не знає App revision. Якщо CAS використовується іншим клієнтом, обидва поля обов’язкові разом і перевіряються строго. Callback engine додатково перевіряє owner/revision/TTL/consumed.
- `recoverReceipt(principal, {channel:'app'|'bot', request})` — exact semantic-input readback після `PRODUCTION_COMMIT_UNKNOWN`. Не викликає context, engine або bootstrap, не надсилає повідомлень. Ledger miss є null; той самий ID з іншим payload/CAS спричиняє conflict.
- `pendingOutbox(principal, limit=50)` повертає лише pending messages цього owner/current session/current control epoch, після власної завершеної transaction; cap100. Порядок — `revision,ordinal,id`, тому кілька turns з однаковим server clock не перемішуються. Це не claim/dispatch/ack API. Повідомлення не стають `sent` від читання або snapshot.

Verified principal — виключно результат чинного server authentication adapter. Structural `verified:true` не є доказом identity. Store перевіряє closed shape та фіксує owner до await; жодного `tg_` prefix inference, body/query owner override чи auto-merge немає. Verified null-owner subscriber mapping допускається лише через окремий trusted callback і чинні перевірки reader.

`context({principal,state,serverNow})` — trusted local catalog/source adapter. Store перезаписує actorId/now server значеннями. Основний display path пропускає plans для owned verified binding із exact address/operator/namespace/target/binding revision, у чинному effective interval, `synthetic:false`, zero cost і валідним ScheduleView. Окремий explicit manual display path дозволяє тільки binding kind `user_selected_group`, status `needs_confirmation` (неіснуючий status `manual_group` не вигадується), ті самі exact fields, current freshness, today/tomorrow, nonfuture observation/publication, source level schedule/address/integration та `deliveryEligible:false`. Він зберігає несертифікований binding, вимкнені персональні сповіщення і явну technical-group notice; це ремонт manual-queue feature, не послаблення delivery gate. Він не робить із технічної групи personal certified plan і не вмикає deliveryEligible. Невалідний або чужий plan не показується. Catalog і source admissions незалежно готує root; цей store не вигадує catalog/плани.

## Gate, bootstrap і атомарність

`PRODUCTION_PROFILE_SCHEMA_SQL` містить лише additive CREATE TABLE/INDEX для `lba_production_control`, `lba_production_profiles`, `lba_production_profile_origins`, `lba_production_bootstrap_ledger`, `lba_production_profile_inbox`, `lba_production_profile_outbox`. Немає auto-DDL, control row seed, reset, destructive migration чи legacy dual-write. DDL default writer_mode — disabled, але відсутня row також блокує всі store paths.

Порядок transaction: BEGIN → singleton control `FOR SHARE` → перевірка `writer_mode='canonical'` та exact epoch → owner advisory transaction lock. Snapshot/bootstrap/mutation/outbox paths мають REPEATABLE READ. **RecoverReceipt має READ COMMITTED:** control SELECT починається до очікування owner lock; його RR snapshot міг би не побачити receipt, який інший writer закомітив під час очікування. Fresh statement snapshot після lock потрібен, щоб null означав підтверджену актуальну відсутність у ledger. Це адресний ремонт reviewer P2; actual two-client PostgreSQL proof виконує root. Відповідний epoch/control writer root повинен змінювати через цей самий control row lock. Row **не доводить**, що старе розгорнуте ПЗ перестало писати: зупинка/фехтування старих webhook/profile/scheduler writers та доказ відсутності обходів — окреме необхідне root cutover work.

SELECT-only `selectLegacyLiveProfileInTransaction(client,principal,options)` викликається всередині caller transaction. Сам helper не виконує BEGIN/COMMIT/ROLLBACK/release. Default `readLegacyLiveProfile` лишається окремим RR READ ONLY wrapper. Bootstrap застосовує exact reader projection лише за відсутності canonical row, provenance і bootstrap ledger. Blocked reader, projection issues та incomplete/orphan mapping блокують створення до виклику будь-якого empty-account verifier. Порожній невідомий профіль не вигадується.

**Явний trusted empty-account port:** `verifyEmptyAccount({principal,client,legacySourceDigest,serverNow})` optional; absent/null default deny. Викликається лише після reconciled ready reader з exact нульовими settings/locations/subscribers та без issues/blockers. Closed result `VerifiedEmptyAccountBootstrap` містить kind `verified_empty_account`, exact ownerId, accountState `new|existing_empty`, opaque accountRevisionId/evidenceRef, exact legacySourceDigest і verifiedAt. Невірний owner/digest, unknown/missing fields, порожні evidence/revision, future proof або verification старіше5хв блокуються. Це TTL поточного server verification, а не вік реєстрації account; старі чинні порожні accounts не відсікаються за created_at.

Caller invariant для root: у **тому самому client/RR snapshot** trusted callback виконує `SELECT id,created_at,updated_at FROM users WHERE id=$principal.ownerId`, звіряє exact чинний authenticated account та застосовні known ownership/link checks. Missing/unknown row або unresolved ownership → null. Реальна схема `users` у `shared/models/auth.ts` має id/created_at/updated_at; не слід вигадувати `registry_revision`, `deleted` чи `disabled` columns. accountRevisionId можна отримати як stable digest дозволених registry fields; evidenceRef лишається opaque і приватним. Callback не використовує tg-prefix/chat inference, request JSON чи email-based auto-merge. Type/структурний proof не замінює фактичної registry перевірки. Local tests перевіряють port contract через inert SQL, не actual account/auth.

Origin source/projection digests, mapped raw private provenance, counts/completeness та verified empty proof записуються окремо від public snapshot. Збережені legacy SQL rows не змінюються. Додатковий insert-only bootstrap ledger містить owner/session/source/origin kind/epoch/time і не має cascading FK до profile/origin: він переживає втрату цих rows. Store не має API його update/delete. Missing profile при ledger або origin забороняє rebootstrap; canonical profile без exact origin/ledger також блокується. Це не автоматична міграція старих pre-ledger canonical rows — потрібне окреме доказове root рішення. Подальші виклики використовують canonical state, навіть якщо власник видалив останню адресу або legacy rows змінилися; empty verifier повторно не запускається.

App/Bot input digest включає immutable normalized semantic input і supplied CAS, але не now, context, plans або поточну revision. Owner є ключем ledger. Inbox replay перевіряється перед engine/CAS і повертає старий receipt; зміна payload/CAS з тим самим ID заборонена. Після 256 engine input IDs durable inbox зберігає dedupe. Provider ingress root має повторно використовувати той самий bot/update ID після timeout/unknown outcome та не обчислювати нову CAS revision для того самого update.

State row порівнюється з owner/session/revision всередині JSON, mutation UPDATE має SQL session/revision predicate. State, notification cancellations, ordered outbox і receipt комітяться разом. Schedule messages зберігають exact accepted ScheduleView і revision linkage, щоб пізніший sender не підкладав свіжий чужий plan. Receipt є «committed, delivery pending/none», а не «Telegram доставлено». Outbox має originating epoch; старий store та старі pending rows не стають доступними через новий epoch. Рішення щодо старої черги при rollback/cutover приймає root явно.

Якщо COMMIT або release після COMMIT має невідомий результат, повертається стабільний `PRODUCTION_COMMIT_UNKNOWN`; потрібен exact-ID recover/retry. Немає автоматичного повторного виконання чи відправлення. SQL40001/40P01/23505 дають `PRODUCTION_TRANSACTION_RETRY_REQUIRED`; RR snapshot до очікування owner lock може спричинити такий конфлікт при конкурентному першому bootstrap. Actual PG concurrency proof ще потрібен.

## Свідомо закриті переходи та незавершені інтеграції

Прямі `/reset` (command/text, bot suffix), callback command `/reset` і `confirm_reset` блокуються до engine. Немає reset route або автоматичного очищення account. Explicit deletion окремої адреси з чинного mutation contract дозволена і має CAS/receipt.

Engine actions `prepare_share`, `record_power_report`, `resolve_legacy_link`, `open_app`, simulated delivery та інші непідключені effects дають `PRODUCTION_EFFECT_HANDLER_REQUIRED` **до** збереження state/outbox/canned reply. Це зберігає чесність результату. Root має додати actual scoped handlers/результати окремо; поточний store не заявляє закриття цих вимог. `persist_profile` і `cancel_pending_delivery` обслуговує власна transaction. Тут не виконуються external effects або literal simulationOnly→false casts.

Не реалізовано provider ingress authentication/chat mapping, durable sender claim/send/unknown/429/403/ack, scheduler events, canonical share/report/account tools або actual cutover. Outbox delivery після commit має окремо повторно перевіряти актуальні policy/binding/owner/epoch і доводити Telegram `ok/message_id`; pendingOutbox не є дозволом відправлення. `handleScheduleEvent` не підключений; його власний event retention512 потребує узгодження перед додаванням event writer.
