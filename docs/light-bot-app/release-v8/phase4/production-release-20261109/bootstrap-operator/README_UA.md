# Явний оператор перенесення профілів

Реалізовано локальний Mac-помічник `tools/prepare-production-bootstrap.command` і його бібліотеку `tools/local-runtime/production-bootstrap.mjs`. Він використовує пряме власницьке PostgreSQL-підключення, чинні canonical store/reader/mapping API та окрему міграційну повноважність. Production-підключень, production-записів і provider-запитів під час розробки цього помічника не виконували.

Це обмежений core-крок випуску: опційне встановлення exact reviewed schema, control, власний bot hold, профілі, origin і bootstrap ledger; окремо — підготовка до майбутнього запуску або posthealthy finalize. Усі 68 вимог залишаються чинними. Цей результат не приймає дизайн, джерела даних, Telegram-доставку, production serving/DB binding або весь продукт. Незалежний reviewer зберігає власні `peer-*` докази окремо; старий peer-висновок стосується лише вказаних у ньому bytes.

## Точні входи

- Поточний незмінний `app/dist-production/build-receipt.json` і повний фактичний inventory вихідних файлів. Помічник виводить current source SHA з реального build receipt, звіряє кожен файл та відхиляє `BOOTSTRAP_SOURCE_BUILD_DRIFT`. Старий candidate `15d3…` не захардкоджений як поточний реліз.
- Canonical schema `3dab788973ff187b372683c0def227da51fd091c2cba94e5ecda04154029e2ce`; повний installed semantic catalog у `expected-canonical-schema.json`, SHA `11a3c8de2fda470f4f4873a89e7579490c33d545055aabfbcf72ea1500c04920`. Перевіряються 50 таблиць,396 колонок, PK/FK/CHECK/UNIQUE, defaults/nullability, індекси/предикати/opclasses/collations; не лише наявність relations. Неочікувані user triggers/rules/policies відхиляються. Допускаються рівно дві початкові форми: 9 legacy таблиць без жодної lba_* relation (`legacy_only`) або 9 legacy +50 повністю відповідних canonical таблиць (`canonical_complete`). Часткова чи невідома schema відхиляється. Для legacy_only план/архів чесно вказують відсутність installed canonical contract; schema3dab у binding є цільовою, не вже встановленою. Окремий paper-preview DDL receipt не є входом цього guard: читається фактичний installed catalog через введене підключення.
- Єдиний секрет — **production Connection string** із Replit Database → Production → Settings. Прихований TTY-ввід; URI/пароль не передаються в argv, журнал, Git, чат або stdout. Для pg_dump пароль є лише в child-process environment. Використовується чинний перевірений parser з `production-backup.mjs`, TLS `verify-full`, системний CA, заборона локального/test URI у production CLI.
- Для застосування — свіжий, фактично підтверджений root-owned fence з `FENCE_AND_ACTIVATION_UA.md`, прив’язаний до поточного source, schema, endpoint HMAC, Replit, старого deployment і positive control epoch. Для зняття hold потрібне **інше** фактичне healthy activation observation.

HMAC target — точна нормалізована parser-ом сукупність `host|port|database|user`, той самий формат, що у чинного release-preflight. `-pooler` не прибирається: для одного плану/застосування потрібний той самий endpoint. Локальний приватний 32-byte identity key спільний із preflight; він не замінює `SESSION_SECRET`.

## Режими та Mac-послідовність

За подвійним клацанням у Finder запускається **тільки читання**. Звичайний запуск зберігає непов’язаний з fence план, який принципово не допускає `--apply`. У Terminal видно запит, куди вставити Connection string через ⌘V і натиснути Return; прихований ввід є очікуваною поведінкою. Немає меню «1/2» і не потрібно копіювати секрет із буфера назад у чат.

Перед реальною передачею root має завершити code/build freeze, незалежне QA та фактичну зупинку всіх старих production/dev writers/senders. Schema або вже повністю відповідає3dab, або встановлюється явним owner-client режимом з точних reviewed SQL bytes після свіжого actual9 R1. Лише після їхніх readbacks root готує конкретні приватні шляхи та коротку команду Mac. Наведені нижче назви `PLAN`/`FENCE`/`ACTIVATION` — позначення входів, а не готові production-артефакти.

| Явний запуск | Результат | Дозволені DB-записи |
|---|---|---|
| Без аргументів | READ ONLY огляд і план; fence не доведений | 0 |
| `--fence FENCE` | READ ONLY план, прив’язаний до SHA фактичного fence та його epoch | 0 |
| `--apply --plan PLAN --fence FENCE` | Свіжий59 R1, core bootstrap на вже встановленій повній schema; власний hold лишається | Лише 5 core таблиць |
| `--apply --plan PLAN --fence FENCE --install-reviewed-schema` | На legacy_only: свіжий9 R1, exact44fc schema install + control/hold в одному TX, потім core bootstrap | Лише reviewed CREATE/ALTER/INDEX та 5 core таблиць |
| `--ready-for-activation --fence FENCE` | Поки всі старі actors справді зупинені: свіжий59 R1 і зняття лише власного hold; майбутній deployment окремо | Один CAS UPDATE bot state |
| `--finalize --activation ACTIVATION` | Після реального healthy canonical релізу зняття лише власного hold | Один CAS UPDATE bot state |

Кожен режим запускається явно. План не переходить автоматично до запису. Apply відхиляє непов’язаний план, інші fence bytes/epoch/source/target, прострочені спостереження, неповну schema або незрозумілий попередній стан. На момент author-перевірки немає фактичного accepted production fence чи activation artifact; вони не створені як приклад і не підмінені fixture-ом.

Шлях launcher на Mac: `/Users/admin/Projects/LIGHT BOT APP [CODEX]/tools/prepare-production-bootstrap.command`. У кожному дозволеному запуску секрет вводиться один раз; те саме підключення повторно використовується для read-only snapshot, native backup і відповідного DB-кроку. SESSION/BOT/JWT/webhook secret цей core-помічник не просить.

## Поведінка bootstrap

1. Прочитати signed plan, поточний build, live schema і branded fence; серіалізувати операторів реальним session advisory lock. Цей lock не є доказом зупинки старого sender.
2. До першого DDL/DML створити новий приватний all-public custom pg_dump R1 з exported RR snapshot. Фактичний `pg_restore --list` має підтвердити всі TABLE DATA поточного source: рівно9 для legacy_only або59 для canonical_complete. Не вимагати неіснуючі canonical tables у9-table backup і не підміняти його синтетичним TOC. Архів — own regular file0600, nlink1, PGDMP, перевірені inode/size/SHA; його original object отримує module-private capability. Прості metadata, copy/deserialized object, callback fake dump або довільний binary не допускаються. Перед DML перевірка архіву повторюється. Наявний каталог/backup не видаляється при EEXIST.
3. За явного `--install-reviewed-schema` і лише для legacy_only завантажити незмінні reviewed SQL bytes `native-schema-peer/native-preview-fixed.sql`, SHA `44fc2c6935c6d73325309431303bbd1b2700d9817c55320b95b7ef588a451112`. Виконати тільки цей allowlisted CREATE/ALTER/INDEX script, звірити повну installed3dab schema й незмінність legacy. DROP, legacy DML, schema guessing чи довільний SQL не підтримуються. За вже повної schema DDL не повторюється. У тій самій control-транзакції створити відсутні canonical control і bot state з обраним root epoch та власним `bootstrap_operator_pending`/operation hash. Існуючий стан допускається лише як exact resume того самого приватного журналу. Невідомі/чужі holds, receipts і cooldown не скидаються.
4. Взяти додатковий реальний TABLE SHARE barrier на 9 legacy tables. Для кожного актуального `users` PK чинний `store.snapshot` виконує **свою справжню транзакцію**, з owner lock та повторною перевіркою registry/own hold/epoch/authority. Міграційний principal означає DB-підтвердженого власника під operator authority; він не засвідчує user login. Не створюються акаунти, provider proofs, HTTP/auth sessions, JWT або cookies.
5. Звірити exact verified legacy projection і повторний snapshot, IDs/session/revision, origins/ledger/provenance; зберегти приватні per-owner digests. Усі 9 legacy table raw JSONB HMAC незмінні; orphan rows, settings references, opt-outs і адреси не перепризначаються. Settings-only exception використовує чинний `retain_owned_profile`, без надання subscriber ownership.
6. Успіх `BOOTSTRAP_VERIFIED_HELD`: import/inbox/outbox/native/campaign/auth ефектів немає, власний hold збережений. Реєстр standalone legacy recipients та свіжа класифікація аудиторії — окрема частина чинного production campaign worker з production SESSION_SECRET; core не дублює eligibility і не стверджує, що розсилка вже готова.

Native DDL та initial control/hold, якщо потрібні, commit-яться разом. Actual DDL failure повертає всі50 таблиць у відсутній стан без зміни legacy. При втраті commit response новий read-only план читає фактичні9 або59 tables:9 означає незакомічений schema-крок;59 потребує exact owned control/hold/journal і не повторює DDL. Далі це resumable послідовність per-owner commits, **не одна глобальна транзакція**. Частково завершений prefix лишається разом із власним hold і signed private journal. Подальша дія — read-only звірка, новий прив’язаний свіжий план/R1 та exact resume, без reimport/overwrites або нового operation ID. Після активного продуктового запису apply rerun не повертає профілі до старої projection: non-core/new revision drift блокує bootstrap. Для звичайної post-cutover роботи використовується finalize/операційний маршрут.

## Явна готовність до запуску і posthealthy finalize

Основний порядок власницького cutover: фактично зупинити старі production/dev actors → readonly bound plan → apply з optional exact schema install → `BOOTSTRAP_VERIFIED_HELD` → окремий `--ready-for-activation` під свіжим підтвердженням тих самих зупинок → `BOOTSTRAP_READY_FOR_ACTIVATION` → root виконує native Publish з фактичним `hasDiff=false` і запускає active canonical app → фактичні provider/HTTPS/native перевірки та дозволена кампанія. Цей порядок усуває цикл, коли startup prepare законно відмовляється працювати під будь-яким bot hold.

Передактиваційний крок не потребує й не вигадує healthy HTTPS. Він перевіряє completed immutable account proofs, повну3dab schema, direct epoch/own hold, незмінні початкові canonical/legacy digests та відсутність native unknown/non-core effects; створює свіжий59 R1 і знімає лише власний hold. Свіже re-observed fence може мати інші bytes після попереднього5хв вікна, але ті самі фактично зупинені ресурси/source/target/epoch. Обидва fence SHAs записуються в lineage. Receipt явно містить `deployedHealthy:false,providerHealthyVerified:false,nativeBotIdentityVerified:false`; нічого не стартує й не розсилає.

Це підтриманий [власницький зовнішній PostgreSQL клієнт Replit](https://docs.replit.com/features/data-and-storage/connection-details), не Replit Agent production executeSql, startup DDL чи новий admin endpoint. Старий read-only API guard не вимикається. Default Finder-огляд не обов’язковий для cutover; фактичний flow має **три явні Mac-запуски**: bound plan, apply, ready. У кожному той самий production DSN вводиться заново в прихований prompt, один раз; секрет не зберігається для наступного запуску. Root звіряє однаковий target HMAC, source, epoch, operation journal та актуальні observations між ними. Apply використовує exact fence SHA свого плану; ready є новою explicit фазою і може використати свіжий same-resource readback. Це окремі контрольовані кроки, а не три різні міграції або автоматичний перехід після readonly plan. До готового actual window власнику не видають placeholder-команду для apply.

Альтернативний маршрут із уже healthy canonical app, якщо його startup допускає такий стан, зберігається як окремий posthealthy `--finalize`; він не використовується для підміни передактиваційної готовності. Після успішного ready немає потреби вдруге «знімати» той самий hold через finalize.

## Невідомий COMMIT і posthealthy перевірка

Окремий finalize потребує immutable completed bootstrap account proofs, actual new deployment success + HTTPS same-build canonical health і прямих DB schema/control/own-hold перевірок. Він бере shared dispatcher bot lock і operator lock, відхиляє dispatching/unknown native attempts та будь-який foreign hold, створює власний свіжий приватний R1 і виконує CAS лише `hold_reason`/`hold_operation` своєї операції.

Зміни профільних preferences/revision/inbox, нові справжні HTTP/auth sessions та users-upsert після activation зберігаються. Перевіряється незмінність первинних origin/bootstrap ledger proofs і відповідність owner/canonical session; raw legacy/profile digest не вимагається незмінним назавжди. Finalize не випускає auth, не викликає Telegram API і не засвідчує native getMe. `configuredBotId` health є configured field; native identity перевіряє dispatcher перед своїм effect.

Перед CAS зберігається signed intent. Для ready діють окремі `BOOTSTRAP_READY_COMMIT_UNKNOWN`, `BOOTSTRAP_READY_RECONCILED`, `BOOTSTRAP_READY_NOT_COMMITTED` та historical `BOOTSTRAP_ALREADY_READY_FOR_ACTIVATION` з такими самими no-blind-retry/no-new-clear правилами. Для posthealthy finalize при втраті COMMIT-відповіді результат `BOOTSTRAP_FINALIZE_COMMIT_UNKNOWN`: повтор виконує readback. Точний committed clear-marker → `BOOTSTRAP_FINALIZED_RECONCILED`; власний hold лишився → `BOOTSTRAP_FINALIZE_NOT_COMMITTED`, без автоматичного повторного UPDATE. Інший стан → explicit blocker. Збережений `finalized` receipt при повторі є лише історичною квитанцією, production writes0; він не знімає новий hold і не підтверджує поточну health.

## Приватні виходи та відновлення

Журнали/плани/R1 розміщуються в `.local/light-bot-app/production-bootstrap/` (directories0700/files0600), signed HMAC; немає raw URI. Публічні docs містять лише synthetic fixture та source/check hashes. R1 утримується до стабільного релізу і погодженого recovery; автоматичного restore/delete production не існує. `restoreVerified:false` чесно означає: native формат/list підтверджений, але новий R1 ще не відновлювався на іншій БД. Чинні окремі restore/rollback/tail-delta докази root лишаються обов’язковими; цей helper не виконує destructive rollback і не закриває весь PROFILE-05/TECH-08.

Оператор повертає лише safe code. На помилці секрет, архів, IDs/chat/address/PII або raw stack у чат не надсилати. Старі/чужі дані не «виправляти» вручну для обходу admission. Root зіставляє private plan/journal/R1 та actual provider readbacks.

## Перевірки та межі

`author-proof.mjs` запускає реальний own-loopback PostgreSQL і allowlisted pg_dump/pg_restore; останній author receipt містить42/42 cases. Це source-bound author evidence, не незалежне приймання або production replay. Fixture source SHA15d3 явно історичний; production CLI перевіряє current actual app build. Історичні c7cdf830/31-case bytes збережено без змін у `historical-c7cdf830-31case/`; вони не переназвані доказом нової ревізії. Перший запуск у sandbox був заблокований shared-memory environment; підвищений запуск дозволив лише owned disposable PG і не послабив production guards.

Механічні дефекти R1, знайдені незалежним reviewer у старих bytes, виправлені та мають окремі regressions: EEXIST preservation, fake/copy metadata rejection, заборона fake dump callback. Додані read-only plan/fence admission, full catalog/hook negatives, actual TABLE SHARE/operator locks, partial prefix/resume/idempotence, legitimate post-cutover delta, native unknown/foreignhold/provenance/session/epoch negatives, before/after real COMMIT outcome recovery, classifier double-catch та privacy/atomic marker checks. Нові actual9→59 cases доводять genuine9 backup/TOC, partial schema/changed SQL rejection, atomic DDL rollback, committed DDL+hold response loss і59-state resume без повторного DDL. Preactivation перевірено без healthy fiction, з foreignhold/source drift, before/after COMMIT recovery та historical no-new-clear. Один початковий розширений запуск зупинився на unqualified synthetic fixture DDL у pg_catalog-first search_path; fixture виправлено на public qualification, а42-case повтор пройшов. Peer review має власний actor і frozen SHA.

Exact next action: root заморожує current app build і приймає незалежний висновок на exact helper bytes; потім actual all-old-writer stop/readbacks і supported owner-client9→59 cutover (або вже підтверджена повна schema). За відсутності supported provider suspension — capability blocker, не JSON-обхід. Лише після цих дій можна готувати конкретний Mac bound-plan/apply/ready handoff. Після READY root окремо перевіряє native Publish hasDiff=false та виконує дозволений deployment/health/campaign маршрут. Відсутність реального fence зараз забороняє production apply; після healthy deployment окремо готується finalize observation.
