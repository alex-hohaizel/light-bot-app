# Паспорт агента відновлення LIGHT BOT APP

**Редакція 1.0 · 7 листопада 2026 · `lba-recovery-agent`**  
**Предмет погодження.** Один директор проєкту з пропонованою назвою входу `light-bot-app-recovery`. У пакеті паспорта є машинний blueprint і предметна модель. Погодження цієї редакції відкриває створення й перевірку агента. Перший аудит продукту, робота з production, зміни GitHub і реліз мають окремо визначені межі.

## 1. Прийняті рішення і ціль

| ID | Рішення власника | Як застосовується |
| --- | --- | --- |
| D-01 | «Регіони як мінімум ті, що вже є», додати всі можливі, якщо дані можна підтвердити на сьогодні. | Мінімум відновлення — **Київ, Вінниця, Одеса, Харків** у фактичному обсязі старого продукту. Області, інші ОСР і населені пункти — розширення з окремим доказом. Публічну карту покриття ведемо на рівні ОСР і території. |
| D-02 | «Без платных апі». | **0 витрат на доступ до API**. Використовуємо доступні без оплати офіційні джерела, погоджені публічні канали та умовно придатні відкриті дзеркала. Платний API попереднього БРИФу вилучено з варіантів. Вартість хостингу й експлуатації обговорюється окремо, якщо з’явиться потреба. |

**Ціль продукту.** Людина зберігає адреси, бачить план відключень із джерелом і датою та отримує зрозумілі сповіщення про важливу зміну. Telegram-бот, веб і Telegram Mini App використовують спільний профіль і графік. Старі користувачі мають відновити доступ до власних налаштувань без повторного ручного внесення підтверджених адрес.

**Пропозиція порядку.** Чотири старі міста залишаються мінімальним критерієм приймання. У P0 звіряємо точний legacy-обсяг та включаємо всі додаткові населені пункти, де старий продукт фактично підтримував адресні графіки. Технічний зріз робимо на одному підтвердженому ОСР. Додаткові території можна вмикати незалежно після їхньої перевірки. Статус «відновлено» для першого релізу можливий після проходження критеріїв усіма чотирма містами. Якщо одне місто блокує джерело, агент фіксує конкретний блокер і варіант повернення. Зміна складу першого релізу в цьому разі потребує рішення власника.

Базові джерела наміру — [попередній БРИФ](https://chatgpt.com/library?file_id=libfile_5de96faac95481918c7b8867fa6f9696&account_id=personal), три відповіді власника в цьому проєкті й перевірений стан GitHub нижче. Обмеження цієї редакції мають пріоритет над ранньою рекомендацією платного API.

## 2. Агент і команда

Одна встановлювана навичка, один директор і одне джерело проєктних рішень. Директор приймає `БРИФ`, `ВІДНОВИ`, завдання виправити інцидент, додати ОСР, перевірити міграцію або продовжити роботу з контрольної точки. Він говорить українською, відділяє факт, гіпотезу і зовнішній блокер, спочатку пропонує перевірний наступний крок. Кінцевий бот залишається детермінованим на маршрутах авторизації, графіка і доставки.

| Компонент | Відповідальність | Вихід і приймання |
| --- | --- | --- |
| Директор `light-bot-app-recovery` | Намір, послідовність етапів, дозволи, інтеграція, Work ↔ Codex, контроль доказів. | Реєстр вимог, журнал рішень, артефакти етапів, перевірена передача. |
| Дані та міграція | Предметний виконавець з незалежними підзадачами джерел, адрес, legacy-аудиту й репетиції. Директор призначає одного відповідального за shared DB й cutover. | Реєстр ОСР, fixtures, golden set, інвентар legacy, dry-run і звірка по акаунтах. |
| App | Чинний `app-atelier-director` для вебу, Mini App, дизайн-системи й спільного виду графіка. | Клієнтські сценарії, стенд, visual QA, збіг даних із Telegram. |
| ChatBot | Чинний `chatbot-atelier-director` для Telegram, діалогу, політики повідомлень, адаптера й тестів. | Версійований автомат станів, приватні картки, повтори й збої, підтверджена поведінка на тестовому боті. |
| Незалежне QA | Окремий виконавець без авторства перевірюваної частини. Доступ до мінімально потрібних, переважно синтетичних даних. | Репродюсери, версії, негативні тести, окремі результати щодо контракту, коду, інтеграції, пристрою і приймання. |

Альтернатива з правилами в репозиторії та двома наявними директорами дешевша для одноразового запуску. Обрана спеціалізація потрібна для довгого супроводу ОСР, даних і міграцій, що перетинають обидва компоненти. Спільні контракти identity, address binding, schedule/event і приватності має одного власника. App та ChatBot отримують окремі типізовані handoff із посиланням на той самий контракт. Склад джерел навичок перевіряється в кожному середовищі. Відсутній спеціаліст означає послідовну роботу або точний handoff. Незалежне приймання в такому разі лишається відкритим до фактичного окремого виконавця.

## 3. Якість даних і критерій розширення

Для кожного ОСР і області застосування ведемо окремі осі доказу.

| Рівень | Що перевірено | Що можна показувати |
| --- | --- | --- |
| **Каталог** | Джерело названо або доступна сторінка оператора. | Посилання на джерело й стан перевірки. |
| **Графік** | Є поточний датований план або підтверджений аварійний режим на визначеній території. | Перегляд перевіреної черги чи стану. Ручний вибір черги позначено як вибір користувача. |
| **Адреса** | Будинок або підключення зіставлено з точним графіком чи чинною чергою. Є перевірка ревізії, правил використання й поведінки при відмові. | Персоналізовані сповіщення для підтверджених адрес після приймання інтеграції. |

Публічна HTML-сторінка, RSS, PDF, повідомлення офіційного каналу і публічний JSON можуть бути входами. Формат, права використання, доступність з цільового середовища, частоту оновлення та обмеження перевіряємо окремо. Зовнішнє дзеркало з тим самим джерелом допомагає діагностиці. Незалежним підтвердженням плану є сам ОСР або окреме авторитетне джерело, що показує той самий scope і дату. Ручні зразки записуємо з датою, статусом і походженням. Закриті доступи й антибот-захист не обходяться. Публічний Nominatim не використовуємо для autocomplete, пошук працює з локальним адресним індексом та документованими дозволеними даними. [Довідник ОСР](https://sies.gov.ua/zvernennya-gromadyan/najbilsh-zapituvana-informaciya/grafiki-vidklyuchen-elektropostachannya-operatoriv-sistemi-rozpodilu) · [Політика Nominatim](https://operations.osmfoundation.org/policies/nominatim/)

**Допуск.** Як стартовий поріг пропоную 20 репрезентативних адрес на ОСР або вичерпний менший набір для вузького покриття та щонайменше 48 годин паралельної звірки графіків. Вибірку розширює lead даних за винятками. Обов’язкові тести: перенесення/скасування, півгодина і північ, перейменування, сусідні будинки з різними планами, кілька вводів, зміна upstream ID, відсутні та застарілі дані, аварійний режим, конфлікт і повтор. Поточний операторський план не є телеметрією електроживлення. Після розбіжності, втрати свіжості або зламаного формату автоматичні сповіщення для зачепленого scope зупиняються, у клієнті видно датований останній план або явний статус невідомості.

**Київ.** Публічний план є адресним. Історичну чергу залишаємо для аудиту міграції. Поточну адресу звіряємо з офіційним результатом ДТЕК. Будь-які технічні ключі YASNO прив’язані до джерела й ревізії. [ДТЕК Київські електромережі](https://admin-stage1.dtek-kem.com.ua/ua/news/u-kiyevi-diyut-individualni-grafiki-vidklyuchen-shcho-vazhlivo-znati-kiyanam)

Рекомендований технічний старт — React/TypeScript і PostgreSQL як продовження фактичного стеку. Проба TypeScript визначає, які безпечні компоненти зберігаємо, де замінюємо ядро й чи виправданий Go. API і worker окремі, дані та контракти спільні. Архітектура, точні SLO, поведінка тихих годин, хостинг і бюджет інфраструктури мають рішення до відповідних етапів.
