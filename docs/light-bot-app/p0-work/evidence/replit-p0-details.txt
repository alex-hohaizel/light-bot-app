Safe isolated probe без правок:
Можливий окремий metadata-процес, який не імпортує застосунок. Саме так виконано дозволені Telegram GET.
Не встановлено безпечного способу запуску всього застосунку без side effects. NODE_ENV=development недостатньо: seed і reconciliation розташовані до відповідних обмежень.
Запуск із read-only DB credentials може блокувати записи помилками, але не робить startup нешкідливим: мережеві запити та інші startup effects залишаються.

5. Чим закрити deployed revision і live-process→DB binding

Уже використані supported read-only методи:
getDeploymentInfo();
listDeploymentBuilds({limit:3});
getDeploymentBuild({buildId,skipLogs:true}).

Вони дали build metadata, але не deployed Git SHA та не DB binding.

Deployed Git revision: blocked на наявному доказовому наборі. Відомий read-only build-detail метод може читати build logs, але там лише потенційно може бути provenance; наявність Git SHA у логах не встановлена. Називати це гарантованим probe не можна.

Live-process→DB binding: blocked. Серед уже встановлених інструментів немає підтвердженого supported read-only доступу до identity фактичного DB connection запущеного процесу або deployment→DB resource mapping. SQL environment:"production" визначає managed target інструмента, не доводить connection target Node.

Для закриття потрібні вже наявні, авторитетні provenance/binding metadata або безпечна діагностика самого serving process. Їх наявність не підтверджена; звичайний запуск застосунку чи довільний GET не є доведено безпечним замінником.
