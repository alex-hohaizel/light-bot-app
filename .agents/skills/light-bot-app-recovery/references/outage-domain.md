# Джерела, адреси і графіки

Застосовувати до LBA-02, LBA-03, LBA-07, LBA-09 і LBA-10. Читати перед підключенням нового ОСР, зміною парсера, міграцією прив’язок або прийманням покриття. Нестабільні відомості про джерело повторно перевіряти на цільовому хості.

## Реєстр покриття

Вести записи за ключем `operator_id × territory_scope × capability`. Населений пункт може мати кілька операторів, а один оператор може мати різні правила для частин території. Нормативні назви й ліцензійний реєстр допомагають ідентифікувати ОСР, фактичну прив’язку будинку доводить його джерело.

Початковий мінімум приймання — Київ, Вінниця, Одеса і Харків та всі додаткові населені пункти, де P0 підтвердив старе адресне покриття. Нові області й ОСР проходять той самий допуск. Один успішний зріз не закриває географію першого релізу.

Для кожного запису зберігати такі поля.

| Група | Поля |
| --- | --- |
| Ідентичність | Стабільний `operator_id`, назва, територія, тип адресного або групового охоплення, origin URL |
| Контракт | Формат, метод читання, схема, права повторного використання, auth requirement, ліміти, версія адаптера |
| Вартість | `access_cost=0`, умови безплатного доступу, дата перевірки, факт відсутності платного резерву |
| Походження | Первинний ОСР, посередник за наявності, upstream chain, незалежність контрольного зразка |
| Чинність | Локальна дата плану, `published_at`, `observed_at`, строк/правило свіжості, статус джерела |
| Доказ | Контрольні відповіді, hashes, порівняння з ОСР, адресна вибірка, результат і власник приймання |
| Операції | Дозволена частота, timeout/retry budget, cache policy, circuit breaker, причина зупинки |

Платні API, платні проксі й платний fallback не входять у цю спеціалізацію. Умови ліцензії коду та права на первинні дані оцінювати окремо. Дзеркало й ОСР, від якого воно отримує дані, не становлять двох незалежних підтверджень. Не обходити закритий доступ, антибот-захист або ліміти.

## Рівні допуску

| Рівень | Вхід | Дозволений результат | Причина відхилення |
| --- | --- | --- | --- |
| `catalog` | Доказ оператора і сторінки джерела | Посилання та статус перевірки | Невстановлений власник або область застосування |
| `schedule_verified` | Поточний датований план чи явний аварійний режим | Показ конкретної перевіреної черги/території | Старий план, шаблон дати, неповний день без позначки, невідомий статус |
| `address_verified` | Чинний зв’язок будинку/підключення з планом плюс source QA | Персональний графік і кандидат на сповіщення | Неоднозначність, застаріла прив’язка, хибний автоматичний вибір |
| `integration_accepted` | Зріз, повтори, відмови, renderer й доставка перевірені | Увімкнення перевіреної можливості за дозволеним release scope | Відкритий due must, відсутнє незалежне QA або право на effect |

Для ручної черги зберігати `user_selected_group` і джерело вибору. Показувати, що користувач вибрав саме чергу. Не подавати цей запис як автоматично підтверджену адресу. Дозвіл на групові сповіщення є окремою продуктовою політикою до P2.

Стартовий метод приймання з погодженого паспорта — 20 репрезентативних адрес на ОСР або вичерпний менший набір вузького покриття та щонайменше 48 годин паралельної звірки. Lead даних розширює вибірку за типами винятків. Проходження часу саме по собі не замінює спостережуваних версій і негативних fixtures.

## Ідентичність адреси

Зберігати `Address` окремо від `OperatorBinding`. Внутрішній `address_id` стабільний при перейменуванні чи зміні upstream ID. КАТОТТГ визначає територію, окремі IDs визначають вулицю й будинок. Для неоднозначного міста або вулиці зберігати район/громаду.

| Сутність | Контракт |
| --- | --- |
| `Address` | Територія, поточна назва, тип вулиці, точний номер, літера/корпус, історичні alias, первісний рядок користувача |
| `AddressAlias` | Назва, мова, тип, період чинності, офіційний документ або джерело, версія |
| `OperatorBinding` | Адреса/підключення, ОСР, namespace зовнішнього ключа, scope `building/connection/operator_group`, `effective_from/to`, source revision, evidence |
| `BindingStatus` | `verified`, `user_selected_group`, `needs_confirmation`, `multiple_supplies`, `unmatched`, `unsupported`, `stale` |

Нормалізувати Unicode, апострофи, пробіли й дефіси із збереженням первісного значення. `12`, `12А`, `12/1` і `12 корпус 1` лишаються окремими кандидатами. Нечіткий збіг і транслітерація дають підказку. Вони не активують підписку.

Пошук проходить територію → вулицю з чинною/історичною назвою → точний будинок → можливе підключення → підтвердження. При колізії назв просити вибір із достатніми ознаками. При кількох вводах показувати варіанти або стан уточнення, зберігаючи одну адресу і кілька доказових прив’язок.

Побудувати власний адресний індекс із дозволених джерел. Публічний Nominatim не застосовувати до autocomplete. Для відкритих реєстрів імпортувати лише дозволені адресні поля. Персональні поля заявників, які можуть бути в реєстрі, виключати allowlist колонок.

Для Києва перевіряти актуальну модель ОСР перед роботою. Адресний індивідуальний план і технічний ключ джерела мають бути пов’язані свіжим доказом для будинку. Стару чергу зберігати як історичне значення. Київська область має окремий namespace і свій контракт. Дату попереднього дослідження не переносити як чинний доказ.

## Канонічний графік

`ScheduleRevision` містить незмінний ID, ОСР, target scope/key, локальну дату, timezone, нормалізовані інтервали, семантичний стан, source revision/URL, `published_at`, `observed_at`, правило дійсності, fingerprint адаптера й raw artifact hash. Точну приватну адресу в загальнодоступний artifact не вкладати.

| Стан | Семантика | Відображення й delivery |
| --- | --- | --- |
| `published` | Підтверджений план для scope і дати | Інтервали з назвою плану й часом оновлення |
| `no_planned_outages` | Джерело явно підтверджує відсутність планових відключень | Чіткий текст із датою й джерелом |
| `possible` | Джерело прямо позначає можливі інтервали | Окремі мітки/штрихування, точне формулювання |
| `not_published` | План ще не оприлюднено | Стан очікування без порожнього «усе працює» |
| `emergency` | Чинний аварійний сигнал із визначеним scope | Позначити призупинення плану лише в його scope, зберегти останню планову версію |
| `stale` | План є, правило свіжості порушено | Датований останній план і ознака застаріння, персональні schedule pushes призупинені |
| `unavailable` | Підтверджене джерело недоступне | Діагностика й контрольоване сервісне повідомлення |
| `conflict` | Чинні джерела суперечать одне одному | Пріоритет ОСР за підтвердженим правилом або ручний розбір, без хибного персонального плану |

Порожній масив, відсутня група, parser exception і невідомий upstream enum дають відхилення або окремий невідомий стан. Відсутність збігу адреси не доводить відсутність відключень. Опублікований план і фактична наявність живлення зберігаються різними подіями.

Інтервали напіввідкриті `[start,end)`. Зберігати точні хвилини без округлення. Для `24:00` кінець є початком наступної локальної доби. На переході DST локальна доба може містити 23 або 25 годин. Неоднозначний час потребує offset/fold чи документованої політики джерела. Неіснуючий час відхиляти до уточнення. Не додавати фіксовані 24 години для переходу календарної дати.

Час публікації відрізняти від часу отримання. Commit timestamp дзеркала і HTTP 200 не доводять чинність payload. Для джерела, яке публікує вікна заживлення, зберігати первинну семантику. Доповнення доби до відключень дозволене лише при явному повному покритті доби й перевірці аварійних/невідомих проміжків.

## Операції й оракули

| Операція | Вхід → вихід | Оракул і відмова |
| --- | --- | --- |
| `certify_source` | Source contract + raw examples → scoped verdict | Зіставити ОСР, дату й контрольні інтервали. Невідомі права/вартість/семантика блокують допуск |
| `resolve_address` | Raw address + aliases + exact operator lookup → binding | Зворотне зіставлення того самого будинку й scope. Кілька кандидатів повертають уточнення |
| `normalize_schedule` | Raw payload + adapter version → revision | Валідний enum, календар, інтервали й scope. Пошкодження зберігає останню версію окремо від помилки |
| `diff_revision` | A + B одного scope/date → semantic transition | A→A не створює зміну, A→B→A створює два переходи. Зміна provenance без зміни плану не є schedule alert |
| `project_view` | Revision + binding + locale/template → ScheduleView | HTML, PNG і текст мають ті самі дату, хвилини, статус і ревізію |

Golden set охоплює стару/нову назву, кілька однакових вулиць, сусідні будинки з різними графіками, кілька ОСР у місті, кілька вводів, зміну upstream ID, півгодину, північ, DST, пустий і пошкоджений feed, затримку, A→B→A й аварійний overlay. Зберігати репрезентативні сирі відповіді без PII та очікувану нормалізовану модель.

При зміні парсера, джерела, прав, правил прив’язки або часової семантики відкривати залежне приймання. Контроль незмінних bytes і hash дозволяє переносити лише незалежні докази. Публічну карту покриття будувати з чинних verdict, кожна можливість має дату й причину обмеження.

## Відновлення після зміни джерела

1. Зберегти raw відповідь, останню прийняту revision і точний parser fingerprint.
2. Порівняти scope, enum, дату й правила адресного lookup з попереднім контрактом.
3. Відтворити розбіжність на fixture без мережевих побічних дій.
4. Виправити адаптер і повторити зачеплені golden cases, включно з невідомим enum.
5. Зіставити новий результат із поточним операторським зразком для тієї самої адреси та дати.
6. Відкрити нову certification revision і дозволити доставку лише в прийнятому scope.

Кешувати читання за однаковим операторським scope, щоб кількість користувачів не множила upstream polling. Адресний lookup виконувати за потребою з обмеженням паралельності й backoff. Тривалість кешу та свіжість плану — різні поля контракту. Політика має власника і виміряний baseline до ввімкнення worker.
